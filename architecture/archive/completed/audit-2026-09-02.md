### P1 - reachable, run- or user-impact

#### F1: R1's restart recovery cannot observe a successful in-flight completion; the completed role is sealed FAILED at the next restart

Chain (every link verified):

1. Restart with an in-flight role -> `resume_incomplete` (called only from
   the FastAPI lifespan startup hook, `api/app.py:19-21`) -> `_execute` ->
   `local_hermes.reconcile()` returns None while the process lives
   (`executors/local_hermes.py:683`) -> `RoleExecutionPending` -> the P-A
   catch at `run_coordinator.py:313-317` returns True; the run stays
   `running`.
2. Nothing in the process ever re-schedules the run. The only `run()`
   schedulers are command acceptance (`service.py:1541`, `:2894`), startup
   `resume_incomplete` (`service.py:392`), and `notify_cancellation`
   (`run_coordinator.py:179-183`). There is no timer, poll loop, or
   read-path trigger for the coordinator lane. The supervised lane has
   exactly the missing machinery (`_spawn_reconcile_watcher`,
   `service.py:562-566`, polling `executor.reconcile` every 5 s); harness
   role executions never register launch records, so that watcher never
   sees them.
3. At the NEXT restart, if the agent process has exited - even after
   completing successfully and writing valid outputs - `reconcile`
   classifies it FAILED from the gone PID alone
   (`local_hermes.py:635-642`; exit_code None, no output inspection), so
   `_validate_and_close` seals `executor.role_failed`
   (`role_execution.py:2844-2855`) and the run FAILS.

Net effect of the R1 fix on the local_hermes lane: instant-FAIL traded for
stall-then-FAIL. The stated intent ("the next resume/notify pass
reconciles") names a pass that does not exist in a long-lived server, and
reconcile is exit-blind after a restart. Note the new Section 11.4
paragraph (documentation sync above) states the normative contract; this
finding is the measured deviation from it.

Coverage gap: the P-A regression test
(`tests/test_run_coordinator_recovery.py:274-328`) manually re-invokes
`coordinator.run(...)` for passes 2-3 (the test harness itself supplies
the wake-up production lacks) and uses `_RestartFakeExecutor`, whose
reconcile returns the true completed result post-"exit" - a capability
the real executor does not have post-restart.

Fix options: (a) spawn an in-process reconcile watcher per acknowledged
execution when `_execute` returns True on Pending, mirroring
`_spawn_reconcile_watcher`; (b) make post-exit reconcile success-aware -
detect completion from on-disk evidence (declared outputs present and
parseable, or a wrapper-written exit marker) instead of mapping "process
gone" unconditionally to FAILED, and let output validation judge the
bytes; (c) both. (a) alone still fails across a second restart; (b) alone
leaves the stall in a long-lived server. Recommended: (c).

#### F2: Switching mode or method on a phase page unmounts the run form and wipes all unpersisted input

`web/src/pages/PhasePage.tsx:43` keys the phase query on
`[projectId, phaseId, mode, selectedMethodId]`; `:97` returns a full-page
`<LoadingState/>` while the new key loads (no `placeholderData` /
`keepPreviousData` anywhere in `web/src`); `RunForm.tsx:135-145` holds the
method specification, supplementary-material fields, history picks,

a mode/method combination therefore replaces the whole page with a

instructions textarea (localStorage draft). Re-selecting within the 15 s

the first time a researcher explores modes.

Coverage gap: `RunForm.test.tsx` renders the form with stable props;
`PhasePage.test.tsx:130` acknowledges the mode-keyed refetch but asserts
only post-settle state.

Fix options: `placeholderData: keepPreviousData` on the phase query
(render the stale view with a busy hint); or lift ephemeral form state
into PhasePage; or move mode-specific configuration into a child query
below the form. Recommended: `keepPreviousData` (smallest change, keeps
the form mounted).

### P2 - correctness, should fix

#### F3: A transient DB error at the execution heartbeat kills the healthy agent process (introduced by P-A)

`execution_observer.py:78-114` (P-A) converts any heartbeat/append/
cancellation-poll exception into `RoleExecutionInfrastructureError`. In
local_hermes that raise happens inside the execute poll loop
(`executors/local_hermes.py:466-470`), whose `finally` terminates the
whole child process tree when `returncode is None` (`:490-495`). Live
micro-reproduction by the lane: raise at the heartbeat point with a
`sleep 30` child -> child killed, returncode -9. The exception then
propagates correctly (run stays `running` per R6), but the agent is dead
and untracked-as-dead; the next pass reconciles a missing PID -> FAILED
closure (F1's exit-blindness). Identical terminal outcome to pre-fix R6,
just delayed - for the highest-frequency DB write in the system (a
heartbeat every poll interval over a 30-75 minute run). The kanban
executor genuinely recovers here (durable task state, no local child).

Fix: treat heartbeat bookkeeping as best-effort inside the executor poll
loop (catch `RoleExecutionInfrastructureError` around `observer.heartbeat`,
log, continue), or suppress the tree-kill when the failure is
harness-side. Recommended: the former.

#### F4: Close-path repository/artifact failures remain run-fatal and unretryable (R6 residual)

`role_execution.py:2901-2914` (`record_artifact` for the closure),
`:2916-2932` (`close_execution` - only `RepositoryConflictError` caught),
`:2955-2969` (`_seal_output`), and the correction-path
`record_validation_attempt` (`:2155-2165`) are all invoked after the try
blocks that re-raise `RoleExecutionInfrastructureError`. A transient DB
error there reaches `run_coordinator.run()`'s generic handler ->
`_handle_error` -> run CASed to FAILED, terminal, excluded from
`list_incomplete_runs` - the closure never sealed despite the agent
having succeeded. Parallel aggravation: `stage_execution.py:132-135`
raises `errors[0]`; if one parallel role is Pending and a sibling hits a
close-path error, declaration order strands the in-flight role.

Fix: wrap the close-path repository/artifact calls in
`RoleExecutionInfrastructureError` (same non-sealing semantics), and in
the parallel path prefer re-raising Pending/Infrastructure over other
errors when both are present.

#### F5: `cancel_run` silently drops the cancellation on a CAS race, and the sealed command makes the loss permanent for that idempotency key

`service.py:2220-2238`: `request_cancellation` can return
`applied=False` with reasons `already_submitted`, `already_applied`,
`cancellation_fenced`, `compare_and_swap_failed`
(`storage/repository.py:510-523`). Only `already_submitted` raises. On
`compare_and_swap_failed` (head bumped by a concurrent lifecycle event
between `get_run` and the CAS - routine on a running run) the
cancellation is not recorded, yet the notifier fires and the endpoint
returns 200. The cancel command was already sealed (`:2205-2212`), so a
client retry with the same idempotency key hits the early return at
`:2168-2172` and never re-applies: the cancel is permanently lost for
that key while the run proceeds to submission.

Fix: raise `CONTROL_HEAD_STALE` on `compare_and_swap_failed` (mirroring
the correction path at `service.py:2571-2585`); keep swallowing only
`already_applied`/`cancellation_fenced`.

#### F6: `settle_cancellation` wedge - intent without acknowledgement permanently strands a run in `cancellation_requested`

A crash between `observer.launch_intent` (`role_execution.py:1596`) and
the acknowledgement inside `executor.execute` leaves a durable intent
with no ack. A later cancel: run -> `cancellation_requested`;
`settle_cancellation` raises `RoleExecutionPending`
(`role_execution.py:2359-2362`); `run()`'s error handler returns True
silently for `cancellation_requested` (`run_coordinator.py:1170-1171`);
`cancellation_requested` is not in CANCELLABLE (`run_views.py:29`), so no
new cancel command can re-notify (the UI reports the misleading
`RUN_ALREADY_SUBMITTED`). Every future restart replays the same raise. No
escape short of database surgery. Tiny window, but permanent and silent.

Fix: in `settle_cancellation`, seal a `cancelled` closure with a
diagnostic when an intent has no ack (an acknowledged-then-killed process
is impossible to address anyway), or escalate loudly instead of raising
into a swallowing handler. Recommended: seal-cancelled-with-diagnostic -
cancellation is a user command that has already been durably accepted;
wedging the run contradicts Section 11.1's "completes cooperative
stopping".

#### F7: Correction replay after a restart burns the bounded HV-5.6 attempt without validating the agent's finished work

D-7 marks the interrupted correction and the user re-issues (by design).
The replay reaches `execute_correction` with a durable ack -> `reconcile`
-> post-restart exit-blindness returns FAILED
(`local_hermes.py:635-642`) -> `_validate_and_close_correction`'s FAILED
branch records the `executor.role_failed` attempt row
(`role_execution.py:2166-2210`): one of the two bounded attempts spent
without ever validating the corrected bytes the agent actually wrote
(R4's materialization skip carefully preserved them). Two restarts ->
`correction_exhausted` on a run the agent may have fixed.

Fix: on a reconcile-FAILED during a correction replay where the process
merely vanished post-restart (no exit code), validate the correction
workspace outputs before spending the attempt, or classify as interrupted
(no spend). Depends on the F1 exit-blindness resolution.

#### F8: R31's mtime rule silently drops same-attempt companion artifacts written before the main output (introduced by ba713a4)

Fix: distinguish "prior attempt" without mtime (exclude files whose
digest already appears in the prior closure's linked artifacts, or key on
the attempt workspace), or accept the companion and let the recorded
digest speak for itself.

## Coverage-gap theme

Three findings (F1, F3, F7) share one shape: the P-A/P-I regression tests
pin the intended semantics with test doubles that possess capabilities
the production executor lacks (a reconcile that sees completed results, a
heartbeat that never raises through a live subprocess, a companion scan
with only the stale-leftover ordering). Regression tests for
recovery-class fixes should drive the real executor's observable
boundary (real subprocess, real PID lifecycle) or explicitly document the
gap they leave.
